## 第 4 張 — NeoPower: Scenario-Based System Simulation

目標時間：90 秒。NeoPower 段的重點頁。

另一項重要工作，是我親自開發了一個自訂系統模擬器，用來測試軟體、除錯和重現錯誤。

平台需要與車載系統和充電設備等多家外部廠商互動。開發時不能反覆呼叫廠商的正式系統，也不能每次重現故障都要求對方配合。因此，我開發模擬器來重現外部廠商的行為；依整合情境，廠商可能扮演 client，也可能扮演 server。這樣就能在本地、可控制的條件下驗證系統。

情境不是隨意編出來的。我們參考正式資料庫裡的歷史日誌、客戶回饋與抱怨，以及過去觀察到的營運問題，定義需要重現的流程與錯誤，再透過模擬器與被測後端互動，檢查行為。

兩個代表例子是：很多公車同時進站，充電需求和系統負載快速上升；以及網路設備故障，造成多個充電站或充電樁同時斷線，讓後端必須處理大量異常事件。

模擬器可以支援功能測試、除錯、錯誤重現與回歸測試。下一頁說明這些測試如何用在部署前後。

延伸與界線：

- 圖中的 client／server 是模擬器可重現的廠商角色，不是額外使用第三方模擬器的主張。
- 10 分鐘版可各用一小段說明兩個代表情境如何從歷史資訊形成案例；不編造協定、事故編號、負載數字或效能改善。
- 模擬涵蓋選定的工作流程與異常條件，不能據此宣稱與所有真實設備完全等價。

## 第 5 張 — NeoPower: Testing & Production Reliability

目標時間：80 秒。

我們在開發或修改功能之後，會先用模擬器驗證相關的正常和異常條件，也做回歸測試，確認既有功能沒有被破壞。必要的部署前測試都通過，才能將更新後的系統部署上線。

上線後還要做驗證。一個例子是充電功率分配演算法：系統依不同車輛的充電需求，分配可用功率。新演算法開發後，可以與原本的版本比較實際運作行為。

我們採用的方法之一，是選擇營運條件相近的充電站。有些站使用舊演算法，另一些站使用更新後的演算法，再收集兩邊的營運資料。

接著一起分析系統日誌、實際營運數據與客戶回饋，判斷新演算法是否達到預期改善，以及是否滿足客戶需求。左邊確認變更可以上線，右邊確認上線後在實際環境的表現。

技術備註與問答：

- 跨站比較是觀察性驗證，不是隨機對照實驗。站點、車流與營運條件仍可能有差異，不能僅憑比較就推論因果或統計顯著。
- 10 分鐘版多說如何將日誌、營運資料與回饋一起判讀，以及條件相近仍有上述限制。
- 本簡報不提供未確認的改善比例或實驗結果，也不延伸其他時間分組方法。

## 第 6 張 — Heterogeneous GPU LLM Serving Across Data Centers

目標時間：105 秒。

接下來介紹我目前正在進行的碩士研究。

我主要研究的是跨 Data Center 的 Heterogeneous GPU LLM Serving Scheduling，也就是如何將不同的 LLM Requests 分配到多個 Data Centers 中的 GPU Clusters，讓這些 GPU 能更有效率地協同運作，目標是提高整體 Serving Throughput，並降低系統功耗。

在這個研究中，我們考慮不同 Data Centers 可能配置不同型號的 GPU。這些 GPU 除了運算能力不同，也可能搭配不同容量的 HBM 和 HBF。

這裡簡單介紹一下 HBF。HBF 的全名是 High Bandwidth Flash，是一種以 NAND Flash 為基礎的高頻寬記憶體技術，目前還沒有廣泛量產並應用在商用 GPU 上。

在記憶體配置方面，我主要參考 SanDisk、SK hynix，以及一些學術研究提出的設計和規格，考慮三種 GPU 記憶體配置。

第一種是 Full-HBM，也就是目前常見、以 HBM 為主要高頻寬記憶體的 GPU。

第二種是 Full-HBF，在概念模型中以 HBF 作為主要記憶體，不配置 HBM。

第三種則是 Hybrid HBM/HBF，在研究設定中同時使用兩種記憶體，例如各配置一半的容量。

另外，在 LLM Inference 中，可以將執行過程分成 Prefill 和 Decode 兩個階段。

Prefill 負責處理輸入 Prompt，通常比較需要 GPU 的運算能力；Decode 則是逐步產生輸出 Token，通常比較受到記憶體頻寬和存取效能的影響。

所以我的研究希望探討，在跨 Data Center 的環境下，如何根據不同 GPU 的運算能力與記憶體配置，將 Prefill 和 Decode 工作分配到合適的 GPU Clusters。

最後希望找到更有效率的 Scheduling Strategy，在提升 LLM Serving Throughput 的同時，降低整體系統的功耗。

技術備註與問答：

- 圖中的 A／B 是不同 GPU 型號與運算能力的概念剖面，沒有指定實際產品或數值。兩個 Data Centers 都可執行 Prefill 和 Decode，配置由排程策略決定，並非固定分工。
- Full-HBF 表示在概念模型中以 HBF 取代 HBM 作為主要記憶體；不代表可以省略所有緩衝、快取或資料管理機制。
- Hybrid 的 50/50 是選定研究配置的容量比例，不是頻寬比例，也不是所有混合架構的要求。
- Prefill 與 Decode 的瓶頸仍會受模型、批次與工作負載影響。較高吞吐量與較低總功耗是研究目標，尚無已達成的改善結果。
- HBF 參數取自公開規格與研究模型，沒有直接量測 HBF GPU。此處不加入缺乏可識別來源的容量、頻寬、延遲或功耗數值。

## 第 7 張 — Research Methodology: System-Level Simulation

目標時間：75 秒，包含簡短進度說明。

在研究方法方面，因為目前沒有辦法直接取得搭載 HBF 的 GPU 硬體，因此我主要採用 System-Level Simulation 的方式進行研究，而不是實際建置這些硬體配置。

模擬需要的 GPU、HBM 和 HBF 效能參數，會參考現有的公開硬體規格，以及學術論文中提出並經過評估的模型，包括運算效能、記憶體傳輸延遲、頻寬與功耗等特性。

在實作方面，我目前以開源的 GPU Cluster Serving Simulator 作為系統架構的基礎，並規劃整合相關學術研究所使用的 GPU Memory 和 Storage Simulators，來模擬不同硬體配置下的記憶體傳輸與功耗行為。

接著，在這個模擬環境中建立多個 Data Centers 和不同規格的 GPU Clusters，研究如何將 LLM Requests，以及 Attention 和 Expert 的分割工作，分配到不同的 GPU 上。

最後透過模擬結果，比較不同 Scheduling Strategies 對系統 Throughput 和 Power Consumption 的影響。

所以這個研究的核心，不只是模擬 GPU 硬體本身，而是建立一套結合 GPU 運算、記憶體特性與 LLM Serving 的系統級模擬環境，並利用它來評估和最佳化跨 Data Center 的 Request Scheduling。

目前已定義研究問題與範圍，完成相關 GPU Serving、HBM／HBF 文獻的初步整理，並探索開源模擬框架作為架構起點。接下來會持續進行記憶體模型整合、Baseline Evaluation 和 Scheduling Experiments。

技術備註與問答：

- 開源 GPU Cluster Serving Simulator 是目前使用的架構起點；GPU Memory／Storage 模型的詳細整合、校正與排程評估仍在進行或規劃中，不宣稱整套系統已完成或通過驗證。
- 先前探索的候選框架包含 LLMServingSim 2.0 與 FlashLab HBFSim；候選評估不等於完成整合或重現實驗。
- 模型輸入包含公開 GPU 規格、既有 HBM 特性、發表的 HBF／NAND Flash 模型，以及論文中曾評估的模擬框架。具體版本、參數來源與適用條件仍需在整合時確認。
- 模型需要足以反映影響排程的計算、記憶體存取及資源競爭行為，並非以 GPU 指令層級逐週期模擬為主。
- 跨資料中心的傳輸與資料搬移成本若影響排程結果，需在實作中納入或明確設定假設；不把網路延遲作為本段主題。
- 評估應明確定義吞吐量、總系統功耗的統計範圍及時間窗口，在可比較的工作負載下比較策略。模擬估計不等於硬體實測，也不能將功耗與能耗混用。
- 尚未提供完成的排程演算法、Benchmark 數字、硬體量測結果或已證實的改善。
